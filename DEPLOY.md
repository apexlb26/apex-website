# Deploying to Render

Render runs a persistent Node process, which is what this app wants:
`server.mjs` serves Next **and** holds the Socket.IO connection open, so a CMS
publish reaches open browsers instantly. That is the main reason to prefer it
over a serverless host here.

## 1. A database first

Render has no managed MongoDB, so the database lives elsewhere. **MongoDB Atlas**
is the normal choice and its free M0 tier is enough for this site.

1. Create a free cluster at <https://cloud.mongodb.com>.
2. **Database Access** - add a user with *Read and write to any database*.
3. **Network Access** - allow Render to reach it. Either:
   - add Render's **static outbound IPs** (Render dashboard → your service →
     *Connect* → *Outbound*), which is the tighter option; or
   - allow `0.0.0.0/0`, which is simpler but leaves the cluster reachable from
     anywhere. The database user's password is then the only thing protecting
     it, so make it a strong one.
4. Copy the connection string:

```text
mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority
```

## 2. Seed it

The site needs content before it can serve anything from the database. Run the
migration **once**, from your machine, pointed at Atlas:

```powershell
$env:MONGODB_URI = "mongodb+srv://user:password@cluster.mongodb.net/?retryWrites=true&w=majority"
$env:MONGODB_DB  = "apex"
npm.cmd run db:migrate
```

It refuses to run against a database that already has content, so it cannot
overwrite live edits by accident.

## 3. Create the service

Push this repo, then in Render: **New → Blueprint**, point it at the repository.
`render.yaml` defines the service; Render will prompt for every value marked
`sync: false`.

Set these in the dashboard:

| Variable                    | Value                                        |
| --------------------------- | -------------------------------------------- |
| `MONGODB_URI`               | the Atlas string from step 1                 |
| `APEX_ADMIN_EMAIL`          | your admin login                             |
| `APEX_ADMIN_PASSWORD`       | a strong password                            |
| `NEXT_PUBLIC_APEX_SITE_URL` | `https://apexlb.tech` once DNS points there  |
| mail vars                   | optional - see below                         |

`APEX_ADMIN_SECRET` is generated by Render automatically. Changing it later logs
every admin out.

Do **not** set `PORT`. Render injects it, and `server.mjs` already reads
`process.env.PORT` and binds `0.0.0.0`.

## 4. Custom domain

Render → Settings → Custom Domains → add `apexlb.tech`, then point the DNS
record as instructed. TLS is issued automatically. Set
`NEXT_PUBLIC_APEX_SITE_URL` to the final URL afterwards.

## Things worth knowing

**The free plan spins down.** After ~15 minutes idle a free service sleeps, so
the next visitor waits up to a minute and any open Socket.IO connection drops.
The blueprint uses `starter` for that reason. Free is fine while testing.

**The health check is deliberately forgiving.** `/api/content/version` returns
200 even when MongoDB is briefly unreachable, so a database blip does not make
Render restart an otherwise healthy process.

**If the database is unreachable, the site still serves.** Public pages fall
back to the JSON bundled at build time (`shared/en.json`, `shared/ar.json`), so
visitors see the last shipped content rather than an error. The admin will not
load or publish - editing a copy nobody can save is worse than a clear failure.

**Mail is optional.** Without `RESEND_API_KEY` or the SMTP group, contact
enquiries and job applications are still stored in the `submissions` collection;
they are simply not emailed. Nothing is lost.

**Images live in the database.** Uploads are base64 in MongoDB, not on disk, so
they survive every deploy. Render's filesystem is ephemeral, which is exactly
why nothing is written to it.

## Redeploys

`autoDeployTrigger: commit` means pushing to `main` redeploys.

Content changes do **not** need a deploy - that is the point of the database.
Publishing from `/admin` is live immediately.
